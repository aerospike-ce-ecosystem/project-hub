# GitHub 워크플로우 현황

:::danger 라벨 트리거 에이전트 자동화는 2026-08-18에 제거되었습니다

이 페이지가 원래 설명하던 **Plan → Implement → Review 파이프라인은 더 이상 존재하지 않습니다.** `agent`, `plan-complete`, `start-implement` 같은 label을 붙여도 아무 workflow도 실행되지 않습니다.

삭제된 파일:

| Repo | 삭제된 workflow |
|------|----------------|
| project-hub | `hub-issue-planner.yml`, `hub-issue-dispatcher.yml` |
| aerospike-py, ACKO, cluster-manager, plugins | `issue-planner.yml`, `agent-implement.yml`, `pr-reviewer.yml` |

결정과 근거: [ADR-0053: 라벨 트리거 에이전트 자동화 제거](../architecture/adr/2026-08-18-remove-label-triggered-agent-automation.md) · 관련 이슈: [project-hub#158](https://github.com/aerospike-ce-ecosystem/project-hub/issues/158)
:::

---

## 왜 제거했는가

파이프라인은 **구현 계획(plan)을 issue 코멘트 본문에서 읽어 실행**했습니다. Plan을 식별하는 유일한 기준은 `<!-- agent-plan-start -->`라는 HTML marker 문자열이었고, **그 코멘트를 누가 썼는지는 전혀 검사하지 않았습니다.**

삭제 직전 `hub-issue-dispatcher.yml:55`의 조회식:

```jq
[.[] | select(.body | contains("<!-- agent-plan-start -->"))] | last | .body // empty
```

- **작성자 검사 없음** — project-hub의 두 workflow와 네 core repo의 `agent-implement.yml` 모두에서 `grep -c "author_association"`가 `0`이었습니다. Public issue에 코멘트를 달 수 있는 누구나 marker가 든 "plan"을 심을 수 있었고, 조회식은 그런 코멘트를 `last`로 우선 채택했습니다.
- **실행 권한이 넓음** — 실행 단계는 조직 전역 PAT(`secrets.GH_AW_GITHUB_TOKEN`)를 씁니다. Workflow의 `permissions:` 블록은 자동 발급 `GITHUB_TOKEN`에만 적용되므로, PAT를 쓰는 순간 선언된 `contents: write`는 실제 권한 범위를 나타내지 않습니다. Core repo의 구현 job은 여기에 `--dangerously-skip-permissions`까지 더해져 도구 수준 게이트도 없었습니다.
- **프롬프트 주입 표면** — `${{ github.event.issue.title }}`가 프롬프트 본문에 그대로 보간되는 지점이 에코시스템 전체에 10곳 있었습니다(project-hub 6곳: `hub-issue-planner.yml:5,53,300,417,549`, `hub-issue-dispatcher.yml:4`).

### 위협 모델을 정확히

**트리거 자체는 인증 없이 발화하지 않습니다.** 두 hub workflow 모두 `on: issues: [labeled]`이고, GitHub에서 label을 붙이려면 해당 repository에 write 권한이 필요합니다. 외부인이 단독으로 파이프라인을 실행시킬 수는 없습니다.

실제 문제는 **권한 분리의 붕괴**입니다. 외부인이 plan 본문을 심어 두고, 그 사실을 모르는 maintainer가 정상 절차대로 `plan-complete` 또는 `start-implement` label을 붙이면, 외부인이 쓴 지시문이 조직 전역 PAT 권한으로 실행됩니다. 심어 둔 plan은 정상 plan과 형식이 같아 육안 구분이 어렵고, 대상 `main` 브랜치에는 required status check가 없어 결과 PR도 자동 게이트를 통과하지 못했습니다.

재도입 조건(작성자 검사, repo 범위 GitHub App token, 도구 allowlist, `env:` 경유 입력 전달, required status check)은 [ADR-0053](../architecture/adr/2026-08-18-remove-label-triggered-agent-automation.md)에 정리되어 있습니다.

### project-hub

|------|--------|------|
| `hub-adr-status-override.yml` | issue `adr-rejected` / `adr-deferred` / `adr-positive` 라벨 | 이미 머지된 ADR 문서의 상태 필드 갱신. Issue 코멘트를 plan으로 실행하지 않으므로 유지 |

## 자동화가 하던 일을 지금은 어떻게 하는가

| 예전 | 지금 |
|------|------|
| Issue에 `agent` label → planner가 계획 코멘트 작성 | 사람이 issue에 계획을 직접 작성. Label은 분류·추적용 |
| `plan-complete` label → agent가 구현하고 PR 생성 | 로컬 개발 환경(원한다면 Claude Code CLI 포함)에서 작업하고 평소처럼 PR 생성. 실행 권한은 개발자 본인 자격 증명 |
| `start-implement` label → dispatcher가 각 repo에 issue 생성 | 사람이 각 repo에 issue를 만들고 hub issue에 링크. 순서는 [ADR-0050](../architecture/adr/2026-04-07-dependency-chain-merge-order.md)의 의존성 체인(`aerospike-py → ACKO → cluster-manager → plugins`)을 따름 |
| PR에 `needs-review` label → reviewer가 최대 5회 수정 루프 | 사람이 리뷰 |
| ADR proposal issue → AI 리뷰 + ADR 문서 PR 자동 생성 | 사람이 ADR 문서를 작성해 PR. 상태 갱신은 `hub-adr-status-override.yml`이 계속 자동 처리 |
| `skill-impact-notify` → hub 분석 → plugins에 자동 dispatch | 알림 issue까지는 자동. 이후 판단·전파는 사람 |

### 새 ADR을 제안하려면

1. project-hub에 `ADR Proposal` 이슈 템플릿으로 issue를 만듭니다.
2. 관련 repo maintainer가 리뷰합니다.
3. 합의되면 `docs/docs/architecture/adr/`에 ADR 문서를 직접 작성해 PR을 올립니다.
4. 머지 후 verdict label을 붙이면 `hub-adr-status-override.yml`이 문서 상태를 갱신합니다.

자세한 절차는 [ADR 목록 페이지](../architecture/adr-index.mdx)의 "새 ADR 제안 방법"을 참고하세요.

## 제거된 파이프라인 기록

아래는 2026-08-18 이전에 동작하던 구조입니다. **현재는 어느 것도 실행되지 않습니다.** 과거 issue와 PR을 읽을 때의 참고용으로만 남깁니다.

```
project-hub
  hub-issue-planner.yml    (adr / cross-repo / epic / skill-impact-review 라벨)
    → AI 검토 + plan 코멘트 + verdict 라벨
  hub-issue-dispatcher.yml (start-implement 라벨)
    → plan 코멘트의 <!-- repo-list: ... --> 파싱 → 각 repo에 issue 생성 + agent 라벨

각 Core Repo
  issue-planner.yml   (agent 라벨)          → plan 코멘트 + plan-complete
  agent-implement.yml (plan-complete 라벨)  → 코드 수정 + PR + needs-review
  pr-reviewer.yml     (needs-review 라벨)   → 리뷰 루프(max 5회) + review-complete
```

워크플로우 사이의 데이터 전달에는 HTML 주석 마크업을 썼습니다. 이 마크업은 이제 아무 workflow도 파싱하지 않으므로, 과거 issue 본문에 남아 있어도 아무 동작을 일으키지 않습니다.

```html
<!-- agent-plan-start -->
<!-- repo-plan:aerospike-py --> ... <!-- /repo-plan:aerospike-py -->
<!-- repo-list: aerospike-py, aerospike-ce-kubernetes-operator -->
<!-- agent-plan-end -->
```

관련 ADR: [ADR-0008](../architecture/adr/2026-03-10-issueops-ci-workflow.md) (Superseded), [ADR-0049](../architecture/adr/2026-04-07-adr-lifecycle-automation.md) (Superseded), [ADR-0043](../architecture/adr/2026-04-07-ci-workflow-suite-standardization.md) (부분 Superseded), [ADR-0039](../architecture/adr/2026-04-07-skill-impact-review-pipeline.md) (부분 Superseded).

### Variables / Secrets 정리 현황

일부 조직 설정은 참조하는 workflow가 완전히 사라졌고, 일부는 `daily-release.yml`이 계속 씁니다. **아래 "계속 사용" 항목은 삭제하면 릴리스 파이프라인이 깨집니다.**

| 설정 | 남은 참조 |
|------|----------|
| `vars.CLAUDE_ALLOWED_BOTS`, `CLAUDE_BRANCH_PREFIX`, `CLAUDE_IMPLEMENT_TIMEOUT`, `CLAUDE_REVIEW_TIMEOUT`, `CLAUDE_REVIEW_MAX_ITERATIONS` | **없음** — 정리 대상 |
| `vars.CLAUDE_BOT_ID`, `CLAUDE_BOT_NAME`, `CLAUDE_MAX_TURNS`, `CLAUDE_MODEL`, `CLAUDE_SETTINGS` | 계속 사용 — aerospike-py / ACKO / cluster-manager / plugins의 `daily-release.yml`이 릴리스 노트 생성에 사용 |
| `secrets.ANTHROPIC_API_KEY` | 계속 사용 — 위 4개 repo의 `daily-release.yml` (`claude_code_oauth_token`) |
| `secrets.GH_AW_GITHUB_TOKEN` | 계속 사용 — 5개 repo의 `daily-release.yml`, `skill-impact-notify.yml`(aerospike-py·ACKO), `ace-plugins-pr-notify.yml`(aerospike-py), ackoctl `release.yml`(Homebrew tap push) |
| `secrets.ORG_READ_TOKEN` | 계속 사용 — project-hub `weekly-pr-stats.yml` (미설정 시 `GITHUB_TOKEN`으로 fallback) |
